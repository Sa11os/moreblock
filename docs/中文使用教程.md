# MoreBlock 中文使用教程

这份教程面向三类人：

- 想给整合包或地图添加自定义装饰方块的资源作者
- 想把自定义方块分发到服务器或客户端的服主
- 想在自己 Mod 里调用 MoreBlock API 的开发者

如果你只想先跑通一次，建议先看“快速上手”和“推荐目录结构”；如果你要长期做内容，建议把整篇都看完。

## 1. 模组用途

MoreBlock 会在游戏运行时读取 `config/moreblock/block` 目录中的方块包，并自动把其中的模型、贴图、显示参数和交互配置注册成可用方块。

它主要适合下面几种场景：

- 给整合包补一批不想单独写代码的装饰方块
- 给服务器维护一套统一分发的建筑素材
- 把 Blockbench 做出来的 GeckoLib 模型快速放进游戏
- 给其他 Mod 提供一套动态方块渲染与交互 API

## 2. 环境要求

- Minecraft `1.20.1`
- Forge `47.x`
- GeckoLib `4.4.2+`
- Java `17`

客户端和服务端联机时，双方都需要安装 MoreBlock；如果方块包内容不一致，玩家会被拦截，无法进入服务器。

## 3. 你需要准备什么

### 3.1 基础工具

- `Blockbench`
- Blockbench 的 `GeckoLib` 插件
- 本仓库自带的 MoreBlock Blockbench 工具脚本：`tools/blockbench/moreblock_blockbench_tools.js`
- 一款能处理 PNG 的贴图工具
- 一款能编辑 UTF-8 文本的编辑器
- 一个能打包 zip 的压缩工具

这里特别说明一下 `Blockbench` 里的 `GeckoLib` 插件用途：

- MoreBlock 最终读取的是 `GeckoLib` 导出的 `*.geo.json`
- 如果你手里的原始项目不是 `GeckoLib` 项目，而是别的 Blockbench 项目格式，通常需要先转换
- 常见情况包括：原本是基岩版模型项目、Java 版普通模型项目，或者其他不能直接导出 `GeckoLib geo.json` 的项目
- 这类项目不能直接拿来给 MoreBlock 用，应该先在 Blockbench 里安装 `GeckoLib Models & Animations` 插件，把项目转换成 `GeckoLib Animated Model`，再通过 `Export GeckoLib Model` 导出 `geo.json`

可以简单理解成：

- 原始项目格式只是你的建模工程格式
- MoreBlock 需要的是 `GeckoLib` 产物格式
- 中间这一步通常就是“先转换项目，再导出”

### 3.2 最少资源素材

做一个最基础的导入方块，至少要准备：

- 一个 `GeckoLib` 模型文件：`*.geo.json`
- 一张贴图文件：`*.png`

推荐再准备：

- 一个配置文件：`*.json`
- 一个物品显示文件：`*-display.json`

### 3.3 文件编码建议

- 所有 JSON 文件统一保存为 `UTF-8`
- 文件名尽量使用小写英文、数字、下划线
- 压缩包文件名推荐使用 `UTF-8` 编码

MoreBlock 对 zip 文件名编码做了一定兼容，但长期维护时还是建议统一用 UTF-8，省掉跨平台乱码问题。

## 4. 快速上手

### 4.1 首次启动

第一次启动游戏后，MoreBlock 会自动创建目录：

```text
config/moreblock/block
```

同时还会生成：

```text
config/moreblock/block/.keep
config/moreblock/block/README.txt
config/moreblock/block/example/example.json
config/moreblock/block/example/example.md
```

说明：

- `README.txt` 是目录说明
- `example` 是示例，不会被当成自定义方块加载
- `example.json` 和 `example.md` 可以直接当模板参考

### 4.2 最快的测试方式

把一个完整方块包文件夹直接放进：

```text
config/moreblock/block/
```

例如：

```text
config/moreblock/block/
└─ blue_chair/
   ├─ blue_chair.json
   ├─ blue_chair.geo.json
   ├─ texture.png
   └─ blue_chair-display.json
```

然后重新启动游戏，或重新启动客户端/服务端，再进入世界测试。

## 5. 推荐目录结构

一个推荐的方块包结构如下：

```text
blue_chair/
├─ blue_chair.json
├─ blue_chair.geo.json
├─ texture.png
└─ blue_chair-display.json
```

字段含义：

- `blue_chair.json`：方块配置
- `blue_chair.geo.json`：GeckoLib 模型
- `texture.png`：贴图
- `blue_chair-display.json`：物品在手持、GUI、地面展示时的显示参数，可选

## 6. 打包格式与载入规则

MoreBlock 支持两种直接投放形式：

- 文件夹
- `zip` 压缩包

### 6.1 文件夹格式

最常见的做法就是直接把文件夹放进去：

```text
config/moreblock/block/
└─ blue_chair/
   ├─ blue_chair.json
   ├─ blue_chair.geo.json
   └─ texture.png
```

### 6.2 zip 格式

也可以直接放 zip：

```text
config/moreblock/block/
└─ blue_chair_pack.zip
```

zip 内部支持以下情况：

- 直接把配置、模型、贴图文件放在压缩包根目录
- 再套一层同名文件夹
- 外层压缩包中放多个子文件夹
- 外层压缩包中混合多个子文件夹和子 zip

例如下面这些都可以：

```text
blue_chair_pack.zip
├─ blue_chair.json
├─ blue_chair.geo.json
└─ texture.png
```

```text
blue_chair_pack.zip
└─ blue_chair/
   ├─ blue_chair.json
   ├─ blue_chair.geo.json
   └─ texture.png
```

```text
all_blocks.zip
├─ chair_pack/
│  ├─ chair.json
│  ├─ chair.geo.json
│  └─ texture.png
├─ lamp_pack/
│  ├─ lamp.json
│  ├─ lamp.geo.json
│  └─ texture.png
└─ bed_pack.zip
```

### 6.3 模组如何判断一个目录是不是方块包

目录满足下面任意条件，就会被当成一个可加载包：

- 目录里存在一个有效配置 JSON
- 目录里同时存在 `*.geo.json` 和 `*.png`

也就是说，配置文件不是绝对必须，但推荐始终提供，后期维护会轻松很多。

## 7. 配置文件说明

### 7.1 推荐写法

推荐每个方块包都写一个独立配置文件。

如果你正在用本项目附带的 `Blockbench` 工具脚本，推荐直接通过插件生成，而不是手写第一份 JSON：

1. 点击 `文件 -> 导出 -> 导出 MoreBlock 配置 JSON`
2. 在弹出的表单里填写方块 `id`、中英文名称、模型文件名、贴图文件名、`display` 文件名，以及坐下、躺下、亮度等参数
3. 确认后即可直接导出一份可用的 MoreBlock 配置 JSON

这样做的好处是：

- 不容易把字段名写错
- 文件名和默认值更容易对齐
- 适合先生成一份模板，再按需要手动微调

手写时也推荐遵循下面这种结构，例如：

```json
{
  "id": "blue_chair",
  "name": {
    "zh_cn": "蓝色椅子",
    "en_us": "Blue Chair"
  },
  "geo": "blue_chair.geo.json",
  "texture": "texture.png",
  "display": "blue_chair-display.json",
  "light_level": 0,
  "supports_sitting": true,
  "seat_height": 0.45,
  "supports_lying": false,
  "lying_height": 0.5,
  "lying_rotation_compensation": 0
}
```

### 7.2 字段含义

| 字段 | 是否推荐 | 说明 |
| --- | --- | --- |
| `id` | 推荐 | 方块短 ID，会参与注册名生成。建议只用小写英文、数字、下划线。 |
| `name.zh_cn` | 推荐 | 中文显示名。 |
| `name.en_us` | 推荐 | 英文显示名。 |
| `geo` | 推荐 | 模型文件名，指向同目录下的 `*.geo.json`。 |
| `texture` | 推荐 | 贴图文件名，通常就是 `texture.png`。 |
| `display` | 可选 | 物品显示文件名。省略时会使用内置默认显示参数。 |
| `light_level` | 可选 | 发光等级，范围 `0-15`。 |
| `supports_sitting` | 可选 | 是否允许右键坐下。 |
| `seat_height` | 可选 | 坐下高度，范围建议 `0-2`。默认 `0.5`。 |
| `supports_lying` | 可选 | 是否允许右键躺下。 |
| `lying_height` | 可选 | 躺下高度，范围建议 `0-2`。默认 `0.5`。 |
| `lying_rotation_compensation` | 可选 | 躺下方向补偿，单位为 90 度，允许 `-3` 到 `3`。 |

### 7.3 交互互斥规则

`supports_sitting` 和 `supports_lying` 是互斥的。

也就是说：

- 只开 `supports_sitting`：可坐下
- 只开 `supports_lying`：可躺下
- 两个都开：两者都不会生效

### 7.4 躺下行为说明

启用 `supports_lying` 后：

- 夜晚行为接近床，可以进入睡觉流程
- 白天也可以躺下
- 但白天不会跳过时间，也不会触发完整睡觉效果

### 7.5 兼容别名

当前版本还兼容一些旧字段名或别名，例如：

- `block_id`
- `registry_name`
- `key`
- `lightLevel`
- `emission`
- `light`
- `supportsSitting`
- `can_sit`
- `canSit`
- `supportsLying`
- `can_lie`
- `canLie`
- `lyingRotationCompensation`
- `bed_rotation_compensation`

不过教程里仍然建议统一使用标准写法，后面维护最省事。

## 8. Blockbench 制作流程

### 8.1 模型格式要求

MoreBlock 读取的是 `GeckoLib` 的 `*.geo.json` 模型文件，不是原版普通方块模型。

所以正确流程是：

1. 打开你的 `.bbmodel` 项目
2. 点击 `文件 -> 插件`，打开插件市场，搜索并安装 `GeckoLib Models & Animations`
3. 确认插件已经安装成功
4. 点击 `文件 -> 转换项目`，在格式列表中选择 `GeckoLib Animated Model`
5. 等项目转换完成，确认当前项目已经处于 `GeckoLib` 可导出状态
6. 点击 `文件 -> 导出 -> Export GeckoLib Model`
7. 导出得到 `*.geo.json`
8. 再给模型准备对应贴图，并按 MoreBlock 的方块包格式整理文件

如果你直接拿原版方块模型或普通 JSON 模型来导入，MoreBlock 不会按预期工作。

如果用一句话概括，就是：

`打开 .bbmodel -> 安装 GeckoLib Models & Animations -> 转换项目为 GeckoLib Animated Model -> Export GeckoLib Model`

### 8.2 hitbox 骨骼规则

MoreBlock 会从模型里读取一个骨骼用于生成碰撞箱。

推荐你显式准备一个名为 `hitbox` 的骨骼组。

如果没有名为 `hitbox` 的骨骼，MoreBlock 会回退为标准整方块碰撞箱，也就是 `1*1*1` 的碰撞体积。

### 8.3 内置 Blockbench 工具脚本

仓库里已经提供了 MoreBlock 专用脚本：

```text
tools/blockbench/moreblock_blockbench_tools.js
```

它能做两件很实用的事：

- 从当前模型导出 MoreBlock 配置 JSON
- 根据当前模型自动生成 MoreBlock 可识别的 `hitbox` 骨骼

### 8.4 插件能生成哪些 Hitbox 模式

脚本里提供了四种模式：

- `simple`：整体一个大盒子，最快
- `complex`：快速体素合并
- `quality`：高质量全局最大盒覆盖
- `greedy`：切片矩形合并

实际建议：

- 原型验证：先用 `simple`
- 一般家具、装饰：优先试 `quality`
- 结构规则、面较整齐的模型：可以试 `greedy`
- 追求速度但又不想太粗糙：用 `complex`

### 8.5 命名建议

建议保持同一套命名：

- Blockbench 项目名：`blue_chair`
- 导出的 geo：`blue_chair.geo.json`
- 配置文件：`blue_chair.json`
- 显示文件：`blue_chair-display.json`

这样后续找资源、排错和批量维护都最方便。

## 9. 物品显示文件 `*-display.json`

`display` 文件用于控制物品在不同视角下的展示变换，例如：

- 手持
- GUI
- 地面
- 物品展示框

如果你不提供这个文件，MoreBlock 会自动生成一套内置默认显示参数，因此“没有 display 文件”不会导致导入失败。

但是下面这些模型建议你自己做 `display`：

- 很高或很扁的家具
- 横向摆放才好看的模型
- 在 GUI 中默认角度很难看的模型

## 10. 从资源到游戏的完整流程

这里给一套推荐的实操顺序：

1. 在 Blockbench 里完成模型
2. 安装 GeckoLib 插件并导出 `*.geo.json`
3. 使用 MoreBlock 脚本生成 `hitbox`
4. 准备 `texture.png`
5. 按需导出或手写 `*-display.json`
6. 手写或用脚本导出方块配置 JSON
7. 把整个文件夹或 zip 放进 `config/moreblock/block`
8. 重启客户端或服务器
9. 进入游戏，用创造栏或命令检查是否成功

## 11. 导入后的注册结果

导入成功后，MoreBlock 会在运行时自动生成：

- 方块
- 对应物品
- 运行时资源包内容
- 语言文件内容
- 方块状态与空模型文件

导入包的实际注册名不是直接等于你写的 `id`，而是会再经过 MoreBlock 的内部规则处理，通常会变成类似：

```text
moreblock:config_block_blue_chair
```

如果同名冲突，还会自动追加序号。

所以你在写教程、兼容脚本或查问题时，最好把“显示名”和“注册名”区分开。

## 12. 联机与同步说明

MoreBlock 会校验客户端和服务端的导入方块包清单。

校验内容不是只看文件名，而是会综合以下内容生成指纹：

- 注册名
- 显示名
- 配置文件内容
- 模型文件内容
- 显示文件内容
- 贴图文件内容

只要其中任意一项不同，都可能被判定为内容不一致。

### 12.1 服务器使用建议

- 服务器和客户端都装同版本的 MoreBlock
- 双方放入完全一致的方块包
- 最稳妥的做法是直接把同一份文件夹或同一份 zip 同步给全部客户端

### 12.2 不一致时会发生什么

如果客户端缺包、多包，或包内容不同：

- 登录时会被拦截
- 或进服后校验失败被断开连接

这是正常保护机制，不是 bug。

## 13. 游戏内命令

当前版本提供两个常用命令：

- `/moreblock block list`
- `/moreblock block check`

### 13.1 `/moreblock block list`

列出当前已读取到的全部导入方块。

适合用来确认：

- 包有没有被识别
- 一次导入了多少个方块
- 注册名大概长什么样

### 13.2 `/moreblock block check`

检查主手里拿着的物品是不是 MoreBlock 导入方块，并显示它来自：

- 哪个文件夹
- 或哪个 zip 压缩包

排查“这个方块到底是从哪个包读出来的”时很好用。

## 14. 常见问题排查

### 14.1 方块没加载出来

优先检查这些：

- 文件有没有放进 `config/moreblock/block`
- 模型是不是 `GeckoLib` 的 `*.geo.json`
- 同目录下有没有可用的 `png`
- 配置里的 `geo`、`texture`、`display` 文件名有没有写错
- JSON 编码是不是 `UTF-8` 且无 BOM

### 14.2 进服务器被踢

先检查：

- 客户端和服务端是否安装了相同版本的 MoreBlock
- 客户端和服务端的导入包是否完全一致
- 是否有人私自改了 JSON、贴图、geo 或 display 文件

### 14.3 方块显示名不对

检查配置里的：

- `name.zh_cn`
- `name.en_us`

如果两个都没写，MoreBlock 会退回使用其他可用名称。

### 14.4 模型能放置，但碰撞不对

检查：

- 有没有名为 `hitbox` 的骨骼
- hitbox 是否是你想要的包围范围
- 是否应该用 `quality` 或 `greedy` 重新生成

### 14.5 手持、GUI 里显示很怪

说明你可能需要自定义 `display` 文件，而不是继续使用默认展示参数。

## 15. 给内容作者的推荐规范

如果你准备长期维护几十个甚至上百个方块，建议统一以下规范：

- 每个方块单独一个文件夹
- 每个方块都写配置文件
- 统一使用 `texture.png`
- geo、json、display 文件都和方块 ID 对齐命名
- 每个模型都显式做 `hitbox`
- 发布前统一打成 zip，便于同步给客户端和服务器

这样后续做版本迭代、修 bug、给服务器发更新包都更舒服。

## 16. API 相关说明

如果你不是把资源包丢进 `config`，而是想在自己的 Mod 里通过代码注册动态方块，可以使用 MoreBlock API。

完整开发文档见：

```text
docs/api.md
```

这里先说最关键的几点。

### 16.1 API 适合什么场景

适合：

- 你已经在写自己的 Forge Mod
- 你想复用 MoreBlock 的动态模型与渲染逻辑
- 你想通过代码注册方块，而不是靠外部配置目录导入

不适合：

- 只想给整合包加几个装饰方块，但不想写 Java

### 16.2 API 方块资源放哪里

API 模式下，资源不放在 `config/moreblock/block`，而是继续放在你自己 Mod 的 `resources` 目录里。

例如你的 `modid` 是 `examplemod`：

```text
src/main/resources/assets/examplemod/
├─ geo/block/blue_chair.geo.json
├─ textures/block/blue_chair.png
├─ models/item/blue_chair.json
└─ lang/zh_cn.json
```

### 16.3 最小注册示例

```java
public static final RegisteredMoreBlock BLUE_CHAIR = MoreBlockApi.builder("examplemod", "blue_chair")
        .name("蓝色椅子", "Blue Chair")
        .resourceBase("geo/block/blue_chair")
        .hitboxBoneName("hitbox")
        .showInMoreBlockTab(true)
        .sitting(0.45d)
        .register();
```

### 16.4 `resourceBase(...)` 会做什么

假设你写：

```java
.resourceBase("geo/block/blue_chair")
```

它会自动推导为：

- geo：`examplemod:geo/block/blue_chair.geo.json`
- texture：`examplemod:textures/block/blue_chair.png`
- display：`examplemod:models/item/blue_chair.json`

如果你的资源路径不是这一套，就改用：

- `geo(...)`
- `texture(...)`
- `display(...)`

分别手动指定。

### 16.5 API 常用参数

| 方法 | 作用 |
| --- | --- |
| `name(zhCn, enUs)` | 设置中英文名称 |
| `resourceBase(path)` | 按固定规则推导 geo、texture、display |
| `geo(...)` | 手动指定 GeckoLib 模型资源 |
| `texture(...)` | 手动指定贴图资源 |
| `display(...)` | 手动指定物品显示资源 |
| `hitboxBoneName(name)` | 指定碰撞箱骨骼名 |
| `showInMoreBlockTab(value)` | 是否显示在 MoreBlock 创造模式页签 |
| `translucent(value)` | 是否按半透明渲染 |
| `lightLevel(value)` | 设置亮度 |
| `sitting(height)` | 启用坐下并设置高度 |
| `lying(height, rotationCompensation)` | 启用躺下并设置高度与朝向补偿 |
| `register()` | 提交注册 |

### 16.6 API 注册后的实际 ID

API 注册出来的方块 ID 形如：

```text
moreblock:examplemod_blue_chair
```

注意这里的命名规则和配置导入模式不完全一样。

### 16.7 API 能监听哪些事件

MoreBlock API 提供三类回调：

- `MoreBlockEvents.onUseBlock(...)`
- `MoreBlockEvents.onPlaceBlock(...)`
- `MoreBlockEvents.onRemoveBlock(...)`

用途分别对应：

- 右键交互
- 放置方块
- 移除方块

如果你在 `onUseBlock` 里返回：

- `PASS`：继续执行 MoreBlock 默认逻辑
- `SUCCESS`、`CONSUME`、`FAIL`：拦截默认逻辑

所以如果你只是想“监听一下”，一般返回 `PASS` 就行。

### 16.8 API 模式下谁负责语言和创造栏

MoreBlock API 会帮你注册动态方块和基础物品，但不会替你的 Mod 管理所有外围内容。

你仍然需要自己决定：

- 语言文件怎么写
- 要不要放进自己的创造模式页签
- 是否额外注册自定义物品类

## 17. 推荐发布流程

如果你准备把一批方块发给玩家或服务器，推荐这样做：

1. 本地完成模型、贴图、配置、display
2. 放进 `config/moreblock/block` 实机测试
3. 用 `/moreblock block list` 检查是否全部读到
4. 用 `/moreblock block check` 检查来源是否正确
5. 确认联机客户端与服务端使用同一份文件
6. 最终把内容整理成 zip 发布

## 18. 一句话总结

如果你是资源作者，记住这四件事基本就够了：

1. 模型必须是 `GeckoLib` 的 `*.geo.json`
2. 贴图至少要有一张 `png`
3. 推荐每个方块都写配置 JSON，且用 `UTF-8` 无 BOM
4. 联机时客户端和服务端必须使用完全一致的方块包

做到这几点，MoreBlock 的导入流程通常都会很顺。
